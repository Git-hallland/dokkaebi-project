# 기술 스택 및 배포 방식 결정 초안

## 문서 상태

- 상태: 결정 초안
- 검토 기준일: 2026-08-28
- 대상 단계: 출시 전 MVP
- 목적: 구현을 시작하기 전에 기술 후보와 선택 기준을 비교하고, 사람의 승인을 받을 권고안을 제시한다.

이 문서는 기술 스택을 이미 확정했거나 프로젝트 생성을 승인했다는 뜻이 아니다. 제품 범위와 운영 요구를 기술 선택 기준으로 번역한 문서이며, 구현 직전 체크포인트에서 각 결정을 다시 확인한다. 애플리케이션 코드, 데이터베이스 스키마, API, 클라우드 자원은 이 문서에서 만들거나 확정하지 않는다.

## 1. 제품 요구에서 도출한 기술 요구사항

`PROJECT_BRIEF.md`, `PRODUCT_SCOPE.md`, `CONTENT_MODEL.md`, `EDITORIAL_WORKFLOW.md`에서 다음 요구가 기술 선택에 직접 영향을 준다.

- 공개 문서는 검색엔진이 안정적으로 읽을 수 있어야 하며, 고정 URL, 메타데이터, canonical, sitemap을 지원해야 한다.
- 공개 페이지와 관리자 작성 화면 모두 모바일 환경에서 사용할 수 있어야 한다.
- `draft`, `review` 콘텐츠와 관리자 기능은 공개 페이지, 공개 API, sitemap, 검색 색인에 노출되지 않아야 한다.
- `Content`, `Claim`, `Source`, 변경 이력, 신고, 게임 버전처럼 관계가 명확한 데이터를 일관성 있게 다뤄야 한다.
- 작성·검수·공개 상태 전환과 누가 언제 무엇을 변경했는지 추적하는 기록이 중요하다.
- 출처의 확인 시점, 유효 기간, 재검수 필요 여부를 검색·필터링할 수 있어야 한다.
- 출시 전에는 공식 정보 기반 문서 5~10개로 운영 흐름을 검증하고, 상세 게임 데이터 구조는 실제 수요를 본 뒤 확장한다.
- 콘텐츠, 출처, 변경 이력과 추후 업로드할 자산을 백업하고 실제 복구 가능성을 검증할 수 있어야 한다.
- 관리자 인증, 서버 측 권한 확인, 중요 계정의 2단계 인증 가능성, 비밀정보 분리가 필요하다.
- 초기 트래픽은 불확실하지만 쇼케이스와 출시 직후의 일시적 증가에 대응할 수 있어야 한다.
- 광고·분석·외부 저장소는 개인정보, 비용, 약관, 운영 종속성을 검토한 뒤 별도로 도입한다.

## 2. 개발 및 운영 조건

현재 합리적인 기본 가정은 다음과 같다.

- 1인 운영을 우선하고, 이후 소수 작성자·검수자가 참여할 수 있다.
- 개발 환경은 Windows이며, 로컬과 운영 환경의 차이를 줄여야 한다.
- 전담 인프라 운영자 없이 콘텐츠 운영과 개발을 함께 수행한다.
- 단기 개발 속도보다 장기 유지보수성, 이해하기 쉬운 구조와 보안 업데이트 지속 가능성을 우선한다.
- 그 범위 안에서 출시 전 변경을 무리 없이 전달할 수 있는 단순한 로컬 환경과 배포 과정이 필요하다.
- 비용은 낮게 시작하되 무료 등급만을 전제로 설계하지 않는다. 광고가 붙으면 비상업적 무료 플랜을 사용할 수 없는 경우도 확인해야 한다.
- 애플리케이션과 데이터베이스의 관측 가능성, 로그 접근, 백업과 장애 복구 절차가 필요하다.

따라서 초기에는 하나의 배포 가능한 애플리케이션으로 구성하는 모듈식 모놀리스를 우선한다. 마이크로서비스, 메시지 큐, Kubernetes, 별도 검색 클러스터처럼 운영 지점을 늘리는 구조는 현재 요구에 비해 비용이 크다.

## 3. 프런트엔드 후보 비교

| 후보 | 장점 | 부담과 위험 | 현재 판단 |
| --- | --- | --- | --- |
| Next.js | React 기반, 서버 렌더링·정적 생성·동적 렌더링을 한 앱에서 선택 가능, Metadata API와 sitemap/robots 규약 제공, 서버 기능을 함께 둘 수 있음 | 서버/클라이언트 경계와 캐시 무효화 규칙을 학습해야 함, 프레임워크 변화 추적 필요 | 권고 후보 |
| Nuxt | Vue 기반의 기본 범용 렌더링, 하이브리드 렌더링과 서버 기능 지원, SEO 사이트에 적합 | 팀의 Vue 경험 여부가 중요하며 현재 문서에서 Vue 선호 근거가 없음 | 충분히 가능한 대안 |
| React SPA | 정적 호스팅과 클라이언트 개발이 단순할 수 있음 | 초기 HTML에 핵심 콘텐츠가 없을 수 있고, 메타데이터·크롤링·공유 미리보기·로딩 성능을 별도로 보완해야 함 | 공개 위키의 기본안으로는 비권고 |
| 전통적 서버 템플릿 또는 정적 사이트 생성기 | 콘텐츠 중심 사이트에 단순하고 빠를 수 있음 | 관리자 작성·검수·인증과 동적 검색을 한 흐름으로 묶을 때 별도 구성 부담이 생길 수 있음 | 범위가 더 단순해질 때 재검토 |

React SPA 자체가 검색엔진에 절대 노출되지 않는다는 뜻은 아니다. 다만 이 프로젝트는 SEO가 핵심 유입 경로이고 문서별 메타데이터와 안정적인 초기 응답이 중요하므로, 서버 렌더링 또는 정적 생성을 기본으로 선택하는 편이 위험이 낮다. Next.js와 Nuxt 모두 이 요구를 충족할 수 있다. 현재는 프런트와 서버를 TypeScript 한 언어로 운영할 수 있고 자료와 생태계가 넓은 Next.js를 우선 권고한다.

## 4. 백엔드 구성 후보 비교

### 후보 A: Next.js 기반 모듈식 모놀리스

공개 페이지, `/admin`, 서버 측 데이터 접근과 제한된 HTTP 엔드포인트를 하나의 애플리케이션에 둔다. 여기서 “하나”는 코드 경계를 없앤다는 뜻이 아니다. 콘텐츠, 출처, 검수, 인증 같은 도메인 모듈과 공개/관리자 경계를 내부에서 분리한다.

- 장점: 배포 단위와 언어가 하나이고, 소규모 운영에 필요한 변경을 빠르게 전달할 수 있다.
- 주의: 관리자 권한 검사를 UI 숨김에 의존하지 않고 모든 서버 작업에서 수행해야 한다. 프레임워크 파일에 업무 규칙을 직접 흩뿌리지 않도록 내부 계층을 분리해야 한다.

### 후보 B: Next.js + 별도 Node.js API

- 장점: 공개 웹과 API의 배포·확장·보안 경계를 독립적으로 관리하기 쉽고, 향후 다른 클라이언트가 생길 때 재사용할 수 있다.
- 부담: 배포, 인증 전달, CORS, 로그, 오류 추적, 계약 테스트와 장애 지점이 늘어난다.
- 적용 조건: 모바일 앱이나 여러 소비자가 동일 API를 사용하거나, 웹과 API의 배포 주기·확장 특성이 실제로 달라질 때 검토한다.

### 후보 C: Next.js + Spring Boot

- 장점: Java/Spring의 명시적인 계층화, 보안·트랜잭션·운영 생태계, 복잡한 업무 규칙이 커질 때의 구조적 선택지가 있다.
- 부담: TypeScript와 Java 두 생태계, 두 빌드·배포 단위, API 계약, 인증 경계를 동시에 운영해야 한다. 현재 1인 MVP에는 중복 비용이 크다.
- 적용 조건: Java 경험을 가진 팀이 합류하거나, 별도 백엔드가 필요한 규모와 복잡성이 확인될 때 검토한다.

### 판단

출시 전 MVP에는 별도 API 서버가 필요하다는 근거가 없다. Next.js 모듈식 모놀리스를 권고하되, 업무 규칙과 데이터 접근을 UI 컴포넌트에 결합하지 않아 향후 분리가 가능하도록 한다. “향후 분리 가능성”은 지금 별도 서비스를 만드는 이유가 아니다.

## 5. 언어 선택

초기 권고 언어는 프런트와 서버 모두 TypeScript다.

- 한 언어와 한 도구 체계로 공개 페이지, 관리자 흐름, 검증 로직을 다룰 수 있어 1인 운영 비용이 낮다.
- Content 상태나 역할처럼 제한된 값과 입력 형식을 정적으로 표현하기 쉽다.
- 타입은 런타임 입력 검증이나 권한 검사를 대신하지 않으므로 서버 경계 검증은 별도로 필요하다.

TypeScript와 Java를 함께 쓰면 각 영역의 장점은 얻을 수 있지만, 현재는 저장소 구조, 빌드, 배포, 모니터링과 라이브러리 업데이트가 이중화된다. 별도 백엔드의 필요성이 확인되기 전에는 Java를 추가하지 않는다.

## 6. 데이터베이스 후보 비교

| 기준 | PostgreSQL | MySQL |
| --- | --- | --- |
| 관계형 모델 | 트랜잭션, 제약 조건, 인덱스를 통한 관계 데이터 관리에 적합 | 동일하게 성숙한 관계형 기능 제공 |
| JSON | `json`/`jsonb`를 제공하며 `jsonb` 인덱싱 가능 | 네이티브 JSON 타입과 관련 함수·인덱싱 전략 제공 |
| 텍스트 검색 | 내장 Full Text Search와 `pg_trgm` 확장 선택지 | 내장 FULLTEXT 인덱스와 검색 기능 제공 |
| 운영·백업 | 주요 관리형 DB 서비스가 지원하며 표준 도구 선택지가 넓음 | 역시 관리형 서비스와 표준 운영 도구가 성숙함 |
| 프로젝트 적합성 | 관계형 콘텐츠를 중심으로 두고 일부 가변 메타데이터와 단계적 검색 실험을 함께 하기 좋음 | 충분히 구현 가능하지만 현재 요구에서 PostgreSQL보다 뚜렷한 우위 근거가 없음 |

권고안은 PostgreSQL이다. `Content`, `Claim`, `Source`, revision과 상태 전환은 관계형 무결성이 중요하고, 일부 유연한 데이터가 필요하더라도 처음부터 모든 것을 JSON에 넣을 이유는 없다. PostgreSQL의 JSON과 텍스트 검색 선택지는 초기 단일 DB 전략에도 잘 맞는다.

MySQL도 기능 부족으로 탈락하는 것은 아니다. 운영자의 기존 경험, 선택한 호스팅의 지원·비용, 실제 검색 검증에서 더 유리한 근거가 생기면 대체 가능하다. 어떤 DB를 선택하든 관리형 서비스의 자동 백업만 믿지 않고 복구 시험, 보관 기간, 시점 복구 가능 여부를 확인한다.

## 7. ORM 및 데이터 접근 후보

| 후보 | 장점 | 부담과 위험 | 현재 판단 |
| --- | --- | --- | --- |
| Prisma | 선언적 모델, 타입 생성, migration 도구와 문서가 있어 관계 모델을 빠르게 다루기 쉬움 | 복잡한 SQL과 DB 고유 기능에서는 추상화 밖의 작업이 필요할 수 있고, 런타임·연결 방식 확인 필요 | 우선 권고 후보 |
| Drizzle | SQL에 가까운 TypeScript API, 비교적 얇은 추상화, migration 선택지 | 현재 버전과 migration 흐름을 구현 시점에 검증해야 하며 운영자가 SQL 책임을 더 직접 져야 함 | 현실적인 대안 |
| JPA/Hibernate | Spring/Java 환경에서 성숙한 영속성·트랜잭션 생태계 | Java 백엔드가 없는 권고안에서는 언어와 서비스 추가 비용이 큼 | Spring 선택 시에만 검토 |
| 직접 SQL/쿼리 빌더 | DB 기능과 쿼리를 세밀하게 통제 가능 | 반복 코드와 migration·타입 일관성 책임이 커짐 | 특정 복잡 쿼리에 보완적으로 검토 |

결정 초안은 Prisma를 우선 후보로 둔다. 다만 구현 직전 작은 검증에서 다음을 확인하고 Prisma와 Drizzle 중 최종 선택한다.

- revision, Claim-Source 관계와 상태 전환을 자연스럽게 표현할 수 있는가
- PostgreSQL migration을 검토·롤백·복구할 운영 절차를 만들 수 있는가
- 관리형 또는 서버리스 배포에서 연결 풀과 migration 실행 경로가 명확한가
- 필요한 인덱스와 DB 고유 검색 기능을 과도한 우회 없이 사용할 수 있는가

이 문서는 필드, 테이블, 외래 키를 확정하지 않는다. ORM을 써도 migration 파일 검토, 제약 조건, 인덱스와 쿼리 성능에 대한 책임은 사라지지 않는다.

## 8. 검색의 단계적 접근

### 출시 전 MVP

- PostgreSQL에서 제목, 요약, 문서 유형 등 제한된 필드를 대상으로 단순 검색을 시작한다.
- 검색 결과에는 공개 가능한 콘텐츠만 포함하고 `draft`, `review`, 내부 보관용 `archived`를 제외한다.
- 작은 데이터 규모에서는 정확한 필터, 고정 URL과 결과 품질을 먼저 검증한다.

### 필요가 확인된 다음 단계

- 오타·부분 일치 요구가 커지면 PostgreSQL `pg_trgm`과 적절한 인덱스를 검토한다.
- PostgreSQL Full Text Search는 선택지지만 한국어 형태소와 실제 게임 용어 검색 품질을 표본 데이터로 검증한 뒤 사용한다.
- 문서량, 검색 지연, 관련도 조정, 동의어·자동완성 같은 요구가 DB 검색으로 감당되지 않을 때 전문 검색 서비스를 비교한다.

초기부터 Elasticsearch와 같은 별도 클러스터를 운영하지 않는다. 검색 엔진을 추가하면 색인 동기화, 장애 복구, 접근 제어, 비용과 개인정보 영향이 함께 늘어난다.

## 9. 관리자 영역 구성

출시 전 권고안은 동일 Next.js 애플리케이션의 `/admin` 영역이다. 관련 문서 연결처럼 초기에는 가벼운 입력 방식으로 충분한 기능을 위해 별도 관리자 프런트엔드와 중복 배포를 만들지 않는다.

단일 앱이어도 다음 경계는 지킨다.

- UI에서 관리자 메뉴를 숨기는 것은 인가로 간주하지 않는다.
- 관리자 페이지뿐 아니라 관리자 Route Handler, Server Action, 조회와 mutation 모두 서버 측에서 인증·인가를 확인한다.
- 생성·수정·검수·공개 같은 모든 서버 작업에서 역할과 권한을 다시 확인한다.
- 일반 사용자용 데이터 조회와 관리자 명령 경로를 코드와 접근 정책에서 구분하고 공개 기능과 관리자 기능의 모듈 경계를 유지한다.
- 공개 응답, 캐시, sitemap에 초안과 검수 데이터를 포함하지 않는다.
- 관리자 오류와 감사 기록에는 비밀정보나 불필요한 개인정보를 남기지 않는다.

별도 관리자 프런트엔드는 관리자 팀, 배포 주기, 보안 경계 또는 기능 규모가 독립될 때 검토한다. URL을 `/admin`으로 둔다는 사실이 보안 수단은 아니다.

### 공개 Content 조회와 캐시 안전 조건

- `draft`와 `review`를 UI 필터에 의존해 숨기는 구조는 허용하지 않는다.
- 공개 페이지, 검색, sitemap, metadata, 관련 문서와 공개 API 등 모든 공개 조회 경로에서 기본 `published` 정책을 서버 또는 데이터 접근 계층에서 강제할 수 있어야 한다.
- `archived`의 조건부 공개와 내부 보관 예외는 `CONTENT_MODEL.md`와 `EDITORIAL_WORKFLOW.md`의 기존 정책을 따른다.
- publish, republish, archive 등 공개 상태가 변경되면 영향을 받는 공개 캐시를 적절히 무효화해야 한다.
- 관리자용 `draft`·`review` 데이터와 공개 캐시를 격리한다.
- 정확한 Next.js revalidation 및 캐시 무효화 방식은 프로젝트 생성 이후 확정한다.

## 10. 관리자 인증 후보

필수 요구는 세션 보안, 서버 측 권한 검사, 계정 회수·폐기, 중요 계정의 2단계 인증 가능성, 감사 기록 연결이다. 작성자·검수자·관리자는 개념적으로 분리할 수 있어야 하지만, 1인 운영에서는 한 사람이 여러 역할을 겸할 수 있다.

| 후보 | 적합한 경우 | 검토 사항 |
| --- | --- | --- |
| Better Auth 등 애플리케이션 내 TypeScript 인증 | 사용자 수가 적고 앱·DB 안에서 세션과 역할을 통제하려는 경우 | 2단계 인증 플러그인, 세션 폐기, CSRF·쿠키 설정, 보안 업데이트와 복구 절차를 직접 운영 |
| Auth.js 계열 | OAuth 중심의 단순 관리자 로그인과 Next.js 통합을 선호하는 경우 | 현재 프로젝트 상태와 마이그레이션 방향, 2단계 인증 요구 충족 방법을 구현 시점에 재확인 |
| 관리형 인증 서비스 | 계정 보안과 MFA 운영 일부를 외부에 맡길 가치가 큰 경우 | 비용, 개인정보·제3자 제공, 데이터 이전성, 장애 종속성과 역할 모델 적합성 |

권고 초안은 Better Auth를 우선 검증 후보로 삼고 중요 계정의 TOTP 기반 2단계 인증을 검토하는 것이다. 이것은 제품 선택 확정이 아니다. 실제 채택 전 작은 인증 PoC에서 서버 측 session 검증, 관리자 role·permission 검증, 세션 쿠키 설정, CSRF 관련 동작, 로그인 rate limiting, TOTP 2FA, 로그아웃·세션 만료와 권한 없는 관리자 요청 거부를 확인한다. PoC를 통과하기 전에는 Better Auth를 확정 기술로 표현하지 않는다. 구현 전 보안 검토에서 공식 지원 상태, 업데이트 정책, 계정 복구, 세션 폐기와 관리자 수를 확인한 뒤 최종 승인한다. 직접 만든 비밀번호·세션 체계는 선택하지 않는다.

## 11. 이미지 및 파일 저장

출시 전에는 권리 조건이 확인되지 않은 게임 이미지를 대량 보관하지 않고, 공식 원문 링크·허용된 임베드와 자체 제작 자산을 우선한다. 따라서 대규모 파일 저장소를 미리 만들 필요가 없다.

개념 후보는 다음과 같다.

- 로컬 파일 시스템: 개발용에는 단순하지만 서버리스나 다중 인스턴스에서 영속성과 동기화를 보장하기 어렵다. 운영 업로드 저장소의 기본안으로 두지 않는다.
- 객체 저장소: 추후 허용된 이미지 업로드가 생기면 원본·파생 파일 보관, 권한, 수명 주기와 백업 범위를 분리하기 좋다.
- CDN: 이미지 트래픽과 지역 분산 요구가 확인될 때 객체 저장소 앞에 둘 수 있다.

저장 공급자, CDN, 이미지 변환 서비스는 현재 결정하지 않는다. 도입 시 파일 형식·크기 제한, 악성 파일 검사, 메타데이터의 개인정보, 삭제·정정 요청, 저작권 근거와 DB-자산 복구 일관성을 함께 설계한다.

## 12. 배포 방식 후보 비교

| 후보 | 운영 복잡도 | 비용 특성 | DB·백업 | 확장과 복구 | 종속성 |
| --- | --- | --- | --- | --- | --- |
| Next.js 친화 관리형 플랫폼(예: Vercel) + 관리형 PostgreSQL | 가장 낮은 편. Git 배포, 미리보기, HTTPS가 편리함 | 사용량과 상업적 이용 조건에 따라 유료 전환 가능 | DB는 별도 관리형 서비스/연동의 백업·복구 정책 확인 필요 | 웹 트래픽 증가는 비교적 쉽게 대응. 애플리케이션과 DB 장애 복구를 따로 검증 | 프레임워크 고유 기능과 플랫폼 기능을 많이 쓸수록 증가 |
| 범용 PaaS/App Service | 중간. 런타임·네트워크 설정이 더 필요하지만 서버 관리는 줄어듦 | 상시 인스턴스와 부가 자원 비용이 발생할 수 있음 | 동일 클라우드 관리형 DB와 운영 정책을 묶기 쉬움 | 수평·수직 확장, 슬롯, 백업 선택지가 있으나 설정 책임 증가 | 클라우드 서비스 구성에 따라 증가 |
| 단일 VPS + 관리형 DB | 높음. OS 패치, 프로세스, 리버스 프록시, HTTPS, 모니터링을 직접 운영 | 작은 고정 인스턴스는 예측 가능할 수 있음 | DB를 관리형으로 분리하면 일부 부담 감소 | 서버 장애·배포 실패·용량 증가 대응 절차를 직접 준비 | 애플리케이션 이동성은 높지만 운영자 의존성이 큼 |
| 단일 VPS + 자체 DB | 가장 높음 | 표면 비용은 낮아도 백업·장애 대응 시간 포함 시 불리할 수 있음 | 백업, 시점 복구, 보안 패치 모두 직접 책임 | 단일 장애 지점이 크고 복구 훈련 부담이 큼 | 공급자 종속은 낮아도 서버 운영 종속이 큼 |

출시 전 권고 방식은 **Next.js를 지원하는 관리형 애플리케이션 플랫폼과 관리형 PostgreSQL의 조합**이다. 첫 비교 대상은 Vercel과 범용 PaaS로 두되 공급자는 아직 확정하지 않는다.

Vercel을 선택한다면 Hobby 플랜은 공식 문서상 개인·비상업 용도이므로 광고 등 수익화 시 적합한 상업용 플랜과 당시 가격을 다시 확인한다. Vercel의 기존 자체 Postgres 상품은 종료되었고 현재는 외부 관리형 스토리지 연동 구조이므로, 애플리케이션 배포와 DB 공급자의 장애·백업·비용을 각각 검토한다.

Prisma와 관리형 PostgreSQL을 배포하기 전에는 serverless 환경의 connection pooling, application runtime용 pooled connection, migration·backup·admin 작업에 필요한 direct connection, backup·restore, region과 비용을 함께 확인한다. 이 체크포인트는 특정 PostgreSQL 공급자를 선택한다는 뜻이 아니다.

어떤 후보든 다음을 비교한다.

- 서울 또는 주요 사용자와 가까운 애플리케이션·DB 리전과 두 자원 간 지연
- 커스텀 도메인, 자동 HTTPS, 배포 롤백, 로그와 경보
- DB 자동 백업, 시점 복구, 보관 기간과 실제 복구 시험 방법
- 트래픽 급증 시 제한, 함수 실행 시간, 연결 수와 예상 비용
- 환경변수·비밀정보 관리와 개발/운영 분리
- 표준 Node.js와 PostgreSQL을 유지해 이전 가능한 범위

Kubernetes는 현재 배포 후보가 아니다. 여러 서비스의 독립 확장·배포와 이를 운영할 인력이 실제로 필요해질 때만 재검토한다.

## 13. 개발 환경 원칙

- Node.js는 프로젝트 생성 시점에 공식 지원 중인 Active LTS 또는 Maintenance LTS 중 프레임워크와 ORM이 함께 지원하는 버전을 고정한다.
- 정확한 Node.js, Next.js, ORM 버전은 구현 승인 직전에 공식 호환표와 보안 지원 상태를 확인해 기록한다.
- 패키지 관리자는 초기에는 Node.js와 함께 제공되고 운영자가 익숙한 `npm`을 우선 후보로 삼는다. monorepo나 성능상 근거가 생기면 다른 도구를 검토한다.
- 잠금 파일을 저장소에 포함하고 개발·CI·운영에서 동일한 설치 방식을 사용한다.
- Git으로 변경을 관리하고 기획 문서, migration, 운영 절차를 코드와 함께 검토한다.
- `.env` 등 로컬 설정 파일과 비밀키는 커밋하지 않고, 예시 파일에는 키 이름과 설명만 둔다.
- 개발·검수·운영 환경의 데이터와 인증정보를 분리한다. 운영 데이터를 로컬로 무단 복제하지 않는다.
- Windows에서 개발하되 경로 대소문자, 줄바꿈, 셸 전용 스크립트에 의존하지 않는지 CI 또는 Linux 배포 환경에서 확인한다.

## 14. 테스트 전략 후보와 우선순위

권고 조합은 TypeScript 단위·서비스 테스트에 Vitest, 실제 브라우저 핵심 흐름에 Playwright, PostgreSQL 연동 부분에 제한된 통합 테스트를 두는 것이다. 도구는 구현 시점에 호환성을 확인한 뒤 확정한다.

### 테스트 층위

- 단위 테스트: 상태 전환 조건, slug 정규화, 출처 유효성 판단처럼 외부 자원이 필요 없는 규칙
- 통합 테스트: ORM migration, 제약 조건, Content-Claim-Source 관계, 공개 범위 쿼리, 신고 대기열 연결
- API/서버 경계 테스트: 인증·인가, 입력 검증, 공개 응답 필터와 상태 전환 거부
- 엔드투엔드 테스트: 관리자 로그인부터 작성·검수·공개까지의 소수 핵심 경로와 공개 페이지 노출
- 운영 검증: 배포 롤백, DB·자산 복구, sitemap/robots 확인, 권한과 로그 점검

### 우선 시나리오

1. `draft`와 `review`가 공개 페이지·공개 API·sitemap·검색 결과에 노출되지 않는다.
2. 인증되지 않았거나 권한이 없는 사용자가 관리자 조회와 변경 작업을 수행하지 못한다.
3. 허용되지 않은 상태 전환과 필수 출처가 빠진 공개 전환이 거부된다.
4. slug의 중복·변경·리디렉션 정책이 정해진 규칙대로 동작한다.
5. Content, ContentSource, Claim, ClaimSource, Source 연결과 수정 이력이 보존된다.
6. 신고가 대상 콘텐츠에 연결되고 공개 상태를 임의로 바꾸지 않으며 검수 흐름으로 이어진다.
7. `archived`의 실제 공개 여부 정책과 최신 문서 안내가 의도대로 적용된다.

테스트 수를 늘리는 것보다 권한 누락과 잘못된 공개처럼 피해가 큰 실패를 먼저 자동화한다.

## 15. 보안 요구사항

- 인증 여부와 역할·리소스 권한을 모든 관리자 서버 작업에서 확인한다.
- 중요 관리자 계정의 2단계 인증, 복구 코드 보호와 세션 일괄 폐기를 고려한다.
- 쿠키에는 운영 환경에서 `Secure`, `HttpOnly`, 적절한 `SameSite` 등 안전한 설정을 적용하고 CSRF 방어를 검토한다.
- 로그인, 신고, 검색 등 남용 가능한 경로에는 입력 검증과 필요 시 속도 제한을 적용한다.
- Source URL, 사용자 신고, 본문과 외부 링크·임베드는 신뢰하지 않는 외부 입력으로 취급한다.
- 저장 및 출력 경계의 검증·이스케이프·정화를 통해 XSS와 위험한 URL을 방지한다.
- 외부 URL을 서버에서 가져오는 기능이 생기면 허용 프로토콜·대상·리디렉션과 응답 크기를 제한해 SSRF를 방지한다. 초기에는 URL 등록만으로 서버가 원문을 자동 수집하지 않는다.
- ORM 사용 여부와 관계없이 매개변수화된 쿼리와 최소 권한 DB 계정으로 SQL Injection을 방지한다.
- DB 계정과 서비스 권한은 최소 권한으로 분리하고 운영 비밀정보를 저장소와 로그에 남기지 않는다.
- 의존성 및 런타임 보안 업데이트, 관리자 로그인 이상 징후와 중요한 상태 전환을 확인할 수 있어야 한다.
- 콘텐츠와 관리자 페이지 특성에 맞는 CSP, 클릭재킹 방지, 콘텐츠 유형 보호 등 보안 헤더를 검토한다.
- 감사 기록은 누가 언제 어떤 콘텐츠를 생성·수정·검수·공개했는지 추적하되 비밀번호, 토큰, 불필요한 개인정보를 저장하지 않는다.
- 백업도 운영 데이터와 같은 수준으로 접근을 제한하고 복구 시험 결과를 기록한다.
- 관리자 URL 비공개나 클라이언트 UI 숨김을 보안 통제로 간주하지 않는다.

구체적인 인증·암호화·로그 보관 방식은 스택과 호스팅을 승인한 뒤 위협 모델과 함께 확정한다.

## 16. 권고 스택 초안

| 항목 | 권고 초안 | 이유 |
| --- | --- | --- |
| Frontend | Next.js App Router의 서버 렌더링·정적 생성 중심 | SEO, 문서 메타데이터, 공개/동적 페이지를 한 프레임워크에서 다루기 좋음 |
| Backend | 동일 Next.js 앱 안의 모듈식 서버 로직 | 현재 규모에서 별도 API의 운영 비용을 피하면서 내부 경계 유지 가능 |
| Language | TypeScript | 한 언어로 공개 웹과 관리자 흐름을 운영해 1인 유지비 절감 |
| Database | 관리형 PostgreSQL | 관계형 무결성, JSON 보완, 단계적 검색 선택지와 관리형 백업 가능성 |
| ORM | Prisma 우선 검증 | 관계 모델·타입·migration의 초기 생산성. 작은 검증 후 Drizzle과 최종 비교 |
| Auth | Better Auth 우선 검증 + 중요 계정 TOTP 고려 | TypeScript 앱 내 세션과 2단계 인증 후보를 함께 검토 가능. 보안 승인 전 확정하지 않음 |
| Hosting | 관리형 Next.js 플랫폼 + 관리형 PostgreSQL | 배포·HTTPS·확장·DB 운영 부담을 낮춤. 공급자와 유료 플랜은 별도 승인 |
| Search | PostgreSQL 단순 검색 → 필요 시 `pg_trgm`/FTS → 전문 검색 | 초기 데이터에 맞춰 복잡성과 비용을 단계적으로 늘림 |
| Admin | 같은 앱의 `/admin`, 서버 측 권한 경계 | 초기 관리 기능을 중복 구현하지 않되 공개 기능과 접근 정책 분리 |
| Testing | Vitest + PostgreSQL 통합 테스트 + Playwright 핵심 E2E | 업무 규칙, 데이터 관계, 브라우저 권한·공개 흐름을 위험도에 맞게 검증 |

이 조합의 핵심은 특정 업체가 아니라 **TypeScript 모듈식 모놀리스 + PostgreSQL + 관리형 운영**이다. 구현 전에 각 제품의 최신 호환성과 비용을 다시 확인한다.

## 17. 현실적인 대안과 전환 조건

### 대안 1: Nuxt 모듈식 모놀리스 + PostgreSQL

Vue/Nuxt 경험이 React/Next.js보다 분명히 높거나, 구현 담당자가 Nuxt 운영을 선호한다면 제품 요구를 유사하게 충족할 수 있다. SEO, 관리자 서버 권한, migration과 백업 기준은 동일하게 적용한다. 단순 취향이 아니라 유지보수자의 숙련도와 작은 프로토타입 결과로 결정한다.

### 대안 2: Next.js + Spring Boot + PostgreSQL

다음 조건 중 여러 개가 실제로 생기면 별도 Java 백엔드를 검토한다.

- 웹 외에 모바일 앱이나 외부 소비자가 사용할 안정적인 API 계약이 필요하다.
- 백엔드와 웹의 배포·확장·보안 요구가 독립된다.
- 복잡한 트랜잭션과 도메인 규칙이 커지고 Java/Spring 운영 역량을 가진 팀이 합류한다.
- TypeScript 모놀리스의 모듈 경계로 해결하기 어려운 문제가 측정된다.

미래 가능성만으로 선제 분리하지 않는다.

## 18. 현재 결정하지 않는 항목

다음은 요구와 사용량이 확인되거나 구현 승인 체크포인트가 오기 전까지 보류한다.

- 최종 호스팅·관리형 DB 공급자와 유료 플랜
- 도메인 등록 업체
- 객체 저장소, CDN, 이미지 변환 공급자
- 광고 플랫폼과 광고 배치
- 분석 제품과 쿠키·동의 방식
- 이메일·알림 발송 서비스
- 전문 검색 엔진
- 별도 캐시 계층
- 메시지 큐와 비동기 작업 플랫폼
- 마이크로서비스 분리
- Kubernetes
- 세부 DB 스키마, ORM 모델과 migration 내용
- `visibility` 같은 추가 상태/노출 필드
- 정확한 런타임·프레임워크·라이브러리 버전

## 19. 결정 표

| 항목 | 추천 | 대안 | 선택 이유 | 나중에 재검토할 조건 |
| --- | --- | --- | --- | --- |

## 20. 구현 전 승인 체크포인트

다음 순서마다 운영자의 명시적인 검토와 승인을 받고 진행한다. 이 문서 작성만으로 어느 단계도 자동 실행하지 않는다.

1. **프레임워크 승인**: Next.js와 Nuxt 중 유지보수 경험, SEO 샘플, Windows 개발과 목표 호스팅 호환성을 확인한다.
2. **핵심 모델 검증 승인**: 실제 DB를 확정하기 전에 Content-Claim-Source-revision 관계와 공개 상태 규칙을 작은 설계 예제로 검토한다.
3. **ORM 승인**: Prisma와 Drizzle로 필요한 관계, migration, PostgreSQL 검색 접근, 연결 방식을 비교한 결과를 승인한다.
4. **인증 보안 승인**: 관리자 수, 로그인 방식, 역할, 2단계 인증, 계정 복구, 세션 폐기, 감사 범위를 위협 모델과 함께 확정한다.
5. **호스팅·비용 승인**: 애플리케이션과 DB 후보별 리전, 상업 이용 조건, 월 비용 상한, 트래픽 초과 비용, 로그와 지원 범위를 비교한다.
6. **백업·복구 승인**: DB와 업로드 자산의 범위, 주기, 보관 기간, 복구 목표와 실제 복구 시험 절차를 확정한다.
7. **프로젝트 생성 승인**: 정확한 LTS 런타임, 프레임워크·ORM·테스트 도구 버전과 잠금 파일 정책을 기록한 후에만 프로젝트를 생성한다.
8. **첫 배포 승인**: 비공식 사이트 고지, 공개 상태 필터, 관리자 권한, sitemap, 비밀정보, 로그, 롤백과 복구 절차를 점검한다.
